# 024 — Stale `bootstrap/cache/config.php` Deploy Incident

## Status

Accepted.

## Problem

Production deploy blocked: `php artisan migrate` failed with
`Error: config/permission.php not loaded. Run [php artisan config:clear] and try again.`, which then
blocked `db:seed` (never reached `packages` table). Separately, `php artisan about` reported
`Environment: local`, `Debug: ENABLED`, `URL: localhost:8000` on the production server.

## Investigation (not assumed)

- `config/permission.php` exists, is git-tracked, and is a complete, unmodified Spatie config file.
- `spatie/laravel-permission` is correctly declared in `composer.json`/`composer.lock` and
  auto-discovered normally -- nothing wrong with the package installation.
- Migration order is correct: `create_permission_tables` (2026_08_14_100044) runs before
  `create_packages_table` (2026_08_15_100045) -- "packages table doesn't exist" was a downstream
  symptom of the batch aborting at the permission-tables migration, not an ordering bug.
- The exact error text comes from Spatie's own migration stub
  (`throw_if(empty(config('permission.table_names')), ...)`). Reproduced that hiding the app's
  `config/permission.php` file alone does NOT trigger it -- Spatie's provider uses
  `->hasConfigFile('permission')`, which merges the package's own bundled default config
  regardless of whether the app published a copy. The empty-config state can only happen when
  Laravel's config cache was frozen at a moment *before* Spatie's provider was registered at all,
  since config caching skips all provider config-merging permanently once active.
- Confirmed this actually happened: `git show 5d374a9:bootstrap/cache/packages.php` (this
  project's very first commit, predating Milestone 2's addition of `spatie/laravel-permission`
  entirely) has no `spatie/laravel-permission` entry. If `php artisan config:cache` was ever run on
  the production server around that point, the resulting `bootstrap/cache/config.php` was frozen
  without a `'permission'` key.
- `bootstrap/cache/config.php` was never committed to git (`git log --all -- bootstrap/cache/config.php`
  returns nothing) -- it's a server-local file, explicitly gitignored (`/bootstrap/cache/*.php`,
  added in the prior incident, see the git-tracked-Pail-provider fix). `git pull` cannot touch or
  remove it. It silently outlives every deploy that doesn't explicitly clear it.
- The same mechanism explains the `local`/`ENABLED`/`localhost:8000` symptom for free: if that same
  early `config:cache` ran before the real production `.env` was in place, `APP_ENV`/`APP_DEBUG`/
  `APP_URL` were frozen at their `.env.example` values (which match exactly) -- and a cached config
  stops re-reading `.env` entirely, so later fixing `.env` on the server had zero effect.

## Root cause

**One stale, server-local `bootstrap/cache/config.php`**, generated by an early `php artisan
config:cache` run before `spatie/laravel-permission` existed in the codebase and before the real
production `.env` was configured. Both reported symptoms are the same cache, not two bugs. No
application code is defective -- `config/permission.php`, the package installation, and the
migration order are all correct as-is.

The actual gap: the deploy runbook (`README.md` § 5) ran `migrate --force` and only rebuilt
`config:cache` *afterward* -- it never cleared the *previous* deploy's cache first. Every redeploy
therefore ran migrations against whatever config was frozen last time, which works fine until a
deploy introduces a config file that didn't exist when that cache was built.

## Fix

`README.md`'s three deploy scripts (VPS, managed-panel, and the referenced troubleshooting
section) now run `php artisan config:clear` immediately before `migrate --force`, on every deploy,
not only the first. Added a Troubleshooting entry for this exact error with the one-time recovery
command sequence. No application code changed -- this was a deploy-process gap, not a code defect.

## Consequences

- Does not touch existing data: `config:clear` only removes a derived cache file; nothing in the
  database is affected.
- The person operating the currently-blocked server still needs to run `php artisan config:clear`
  manually once, since the runbook fix only prevents this from recurring on *future* deploys --
  see the Troubleshooting section added to `README.md` for that one-time recovery.
- This is the second incident in this project's history caused by a `bootstrap/cache/*.php` file
  going stale relative to the checked-out code (the first: `Laravel\Pail\PailServiceProvider not
  found`, caused by *committing* `packages.php`/`services.php`, fixed by gitignoring them). This one
  is different in kind -- the file was never committed, it's purely a server-local artifact that
  outlived its own cache-invalidation step -- which is why the fix here is a deploy-process change,
  not a git-tracking change.
